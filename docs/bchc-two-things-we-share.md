# The two things we share, and how they fit together

Written 2026-10-09 from the owner's own explanation. Read this before writing or changing any slide, title or story line in the BCHC talk, especially Part 3 (how we build) and Part 4 (sharing).

## 1. The agentic development process

- This is how we build software: AI agents plan, build, test and review, and a person approves every release. It covers the design system, the roughly 145 tested modules, the source data, the Monday-to-Friday week, agents splitting up the work, testing, review, memory and a person's approval.
- It stands on its own. It does not depend on the use case catalog and is not part of it.
- It isn't just for building web pages or this one site. Health departments can use it to build their own tools, data pipelines and any other technical work.
- We are sharing it with the other health departments (the agentic skills in December, then our source code once it's cleared), so they can build for themselves.

## 2. The use case catalog (the Public Health AI & Tech Exchange)

- This is one thing we built *with* the process. It's a product of the process, not the process itself.
- We are sharing it too. It's where departments post what they've built: AI tools, data pipelines, dashboards, open source work and anything technical they want to share, whether or not they used AI to make it.

## How they fit together

1. A department posts something it built to the catalog.
2. Another department running our agentic process takes that item from the catalog and pulls it into its own process.
3. The process adapts the item, or builds from it, so it fits that department. Now the second department has the tool too.

The modules make building faster because agents start from tested parts instead of a blank page. The catalog extends that idea beyond our own modules: it becomes a shared library everyone can pull from, and the process tailors each piece to the department using it.

## What this means for the slides

- Never describe the catalog as sitting "on top of" the process, or the process as part of the catalog. They are two separate things we share.
- Part 1 shows the catalog as proof: we built it with the process.
- Part 3 explains the process on its own terms, as a general development system rather than "how we built the catalog".
- Part 4 joins them up. Departments share in the catalog, and anyone running the process can pull from it and adapt what they find. The catalog extends the modules.
- Part 5 lists what we're releasing: the process (skills, source code, how to build a design system, workshops). The catalog is already live.
